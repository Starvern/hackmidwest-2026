## Build order

1. **Reproducible setup.** Verify Node/npm runtimes, add the required TypeScript dependencies and runnable Node/contract checks. Document clean-checkout installation/test commands. Keep dependency/configuration changes under one owner.
2. **Runtime contracts.** Implement agreed Zod types, explicit nullable/status fields and discriminated decision unions. Generate JSON schemas and TypeScript types, or provide an automated parity check if a generated mirror is impractical. Make drift fail checks.
3. **Validation tests.** Cover invalid fields, duplicate IDs, nonfinite numbers, quantity/timing/funding bounds, positive acquisition cost, baseline rules, provenance coverage, 12 historical records and 61 indexed states. Verify conflicting reused investment keys fail clearly. Model version, revision, canonical fingerprint and seed semantics must be explicit.
4. **Support early engine integration.** Validate Person 2's fixture and Person 1's result objects. Prepare API route structure and adapter tests while accounting work proceeds; do not advertise a working simulation route backed by fake forecasts or unfinished stubs.
5. **Complete deterministic contract freeze.** Validate the real baseline/truck-only/combined 61-record response with Persons 1 and 2. Ensure null semantics, units, computed deltas and all required inspector fields are present. Commit the generated example with Person 1 and announce the exact accepted revision.
6. **Live API.** Connect the tested engine to the five specified endpoints. Route handlers validate and serialize; they do not calculate business results. After Gate C, wire Monte Carlo to Person 2's real runner/aggregator.
7. **SvelteKit dashboard.** After deterministic acceptance, extend the existing SvelteKit starter and build against the accepted computed response. Use the same client for live endpoints; show MC as not run until valid results exist. Optional AI comes after end-to-end acceptance.

Project scaffolding and API plumbing may proceed alongside deterministic development. Product dashboard development and stochastic result integration must respect the deterministic-first gates.

## API compatibility requirements

- Implement GET `/api/v1/company/demo`, POST `/api/v1/simulate/deterministic`, POST `/api/v1/simulate/monte-carlo`, GET `/api/v1/model/metadata`, GET `/api/v1/health`.
- Deterministic requests reject MC configuration under the published contract. MC requests require explicit enabled settings and bounded runs/seed.
- Invalid user input returns structured 4xx; engine/invariant failure returns 5xx with internal logging, never a success payload.
- Responses carry schema/model/revision, fingerprint, run ID, seed, assumptions, paths, backend comparisons and warnings.
- Serve UI and API from the same origin; retain SvelteKit origin protections. No secrets in browser bundles.
- Agree fingerprint canonicalization with Person 1. Do not implement a conflicting hash in routes and engine.

## Frontend acceptance

- Decision editor supports trucks, hires and marketing with timing, financing and validation.
- Timeline displays opening month 0 and forward months 1–60, baseline/scenario lines and scheduler/metrics events.
- Six metric modes use correct units; reserve line appears only on cash.
- Inspector and comparison cards use engine fields/deltas; no frontend financial formulas.
- Show explicit null/unavailable valuation and reached/not_reached/not_applicable payback states; never render null as zero.
- Distinguish deterministic result, MC mean/median, pointwise bands and horizon-wide shortfall probabilities. No fabricated bands when MC has not run.
- Support stale results after edits, pending/error/retry states, keyboard access and tabular selected-month values.
- Display synthetic-data provenance, assumptions, model limitations and version.
- Verify selected-month values, exit values, events and warnings agree with the accepted payload and live API. Gate D is an integration check, not only a screenshot review.

## Parallel work and merge rules

Use your own checkout/worktree and branch, such as `codex/contracts-api`. Your agents can own schema tooling, API and later frontend separately once dependencies are ready. Give each exclusive files; keep package manifests/lockfiles, generated contracts and shared configuration under one coordinated owner.

Merge setup/schema changes first through Person 1. Keep generated artifacts reproducible. For a contract change, document reason, affected consumers, revision/migration and tests; obtain Person 1's integration decision and Person 2's review where operations/data are affected. Update schema, generated artifacts and all consumers together before release. No silent renames or duplicated frontend types.

After each integration, update/rebase dependent branches and run relevant contract/server/frontend checks. Do not let asynchronous agents continue unknowingly against an obsolete revision; their assignments must name the accepted dependency commit.
